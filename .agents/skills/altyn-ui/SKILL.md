# Altyn UI: единый рабочий навык

## Источники и приоритет

- Требования и API определяют содержание, переходы, данные, ошибки и бизнес-логику.
- `docs/mobile-screen-layout.md` — **единственный нормативный документ** по компоновке и правилам компонентов: сетка, отступы, списки, Input.mobile, модалки, селекторы.
- `docs/ux-writing-guidelines.md` — единые правила текстов.
- **Altyn.Base в Figma** определяет оригинальные компоненты, реальные варианты, размеры, свойства и визуальный вид; подтверждённые референсы Altyn App определяют композицию конкретного экрана.
- `shared/` — частичная HTML-библиотека, **не** визуальный эталон Figma. API, поддержанные варианты и ограничения — `shared/README.md`.
- JSON конкретного сценария хранит его Node ID, результаты проверки, решения и исключения. Не переносить локальные решения в глобальные нормы.

Не выдумывать business rules, component IDs, variants, URL, состояния или сопоставления. Если несколько правил конфликтуют, отличать **глобальное правило** от **контекстного референса**; неопределённое помечать. Не править исходный UI kit без разрешения.

## A. Новый интерактивный прототип → Figma

1. По требованиям/API описать экраны, состояния, переходы, ошибки и вопросы. Не добавлять необоснованные шаги.
2. Просмотреть `shared/`, токены и действующие прототипы. Использовать доступные компоненты; отсутствующее расширять локально, не переписывать общую библиотеку без разрешения.
3. Собрать **интерактивный** HTML/CSS/JS: формы, переходы, расчёты, валидация, модалки, loading/disabled и ошибки. Тестовые настройки — вне пользовательского макета.
4. Проверить **Playwright с Chromium**: сценарии, формы, JS/ресурсы, ширины **390 и 1440 px**, темы — если есть. Опубликовать через GitHub Pages и проверить публичную версию через Playwright; не выдавать локальную за опубликованную.
5. После согласования UX сопоставить HTML с реальными компонентами Figma. Для сложного переноса создать/обновить `<сценарий>/figma-mapping.json`, где отдельно указаны source и target. Показать визуальную разметку и спорные элементы пользователю.
6. После разрешения собрать в Figma **редактируемые связанные instances**. Проверить версии компонентов, свойства, слоты и Auto Layout; не переносить HTML как плоское изображение.

## B. Адаптация готовых веб-/Figma-макетов → Altyn.Base

1. Инвентаризировать существующие экраны, состояния и исходную композицию. Проверить целевые референсы и оригинальные компоненты Altyn.Base.
2. Для каждого элемента определить source node/selector, target component, **реальные** variant properties и степень уверенности. При отсутствии готового соответствия проверить локальные компоненты Altyn App; затем составную композицию из настоящих instances. Не выдавать визуальное сходство за функциональную эквивалентность; фиксировать `Custom / Unmapped` и причину.
3. При запросе «сначала предложи разметку/решение» **не менять Figma** до согласования. Если сборка разрешена, собрать репрезентативный кадр, проверить и продолжить остальные.
4. Создавать новую секцию **рядом с исходной** при соответствующем запросе. Не трогать оригиналы. Содержание/логика берутся из исходного сценария, дизайн/варианты — из Altyn.Base, композиция — из подтверждённого референса.
5. Через Figma MCP проверить происхождение instances, реальные варианты, иконки, Typography, переменные, вложенные слоты, Auto Layout и визуальное совпадение; исправить расхождения.
6. Сохранить Node ID новых кадров, результаты проверки и открытые вопросы в mapping **конкретной задачи**. Не устанавливать `user_approved` до явного согласования.

## Обязательная проверка перед сдачей

- Сверены **компонент, вариант и композиция вокруг него**, а не только названия слоёв.
- Выполнены общие правила `docs/mobile-screen-layout.md`: внешняя сетка, интервалы, непрерывные списки, фоны/радиусы, заголовки, поля.
- Сохранены связанные instances, корректные иконки и Typography/Icons.Core; нет самодельных замен существующих компонентов.
- У Input.mobile label внутри поля, корректные Focus/Invalid; у Bottom Sheet штатные handle/Slot, Secondary-фон, белые списки, кнопки M и safe-area.
- Нет перекрытий, обрезания, потерянных данных, отсутствующих состояний/сценариев; проверены ошибки и длинные тексты.
- Зафиксированы источник, исключения, `Custom / Unmapped`, внесённые изменения, ссылки и ограничения. Новые **подтверждённые общие** правила — только в `mobile-screen-layout.md`, без дубликатов. Новые MD/skill не создавать под отдельные экраны.

Результат сообщать с URL Figma/Pages, перечнем файлов и коммитом, выполненными проверками и открытыми вопросами.
